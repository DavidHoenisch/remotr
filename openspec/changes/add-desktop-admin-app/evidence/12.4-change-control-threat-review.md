# 12.4 Change-control desktop threat review

## Decision and scope

The desktop may expose `change watch`, `authorize`, `pause`, `resume`,
`revoke`, `baseline-promote`, and `baseline-adopt` only with the controls below.
The review covers OS-DOA-016, OS-DOA-017, OS-DOA-019, OS-DFV-022,
OS-DFV-023, OS-DFV-027 through OS-DFV-029, OS-DFA-001 through OS-DFA-004,
and OS-DFA-026 through OS-DFA-028. The public seams are the purpose-specific
Wails backend methods using the selected mutual-TLS Admin API profile, the
native baseline-plan file chooser, and the rendered Change request workspace.

The server's RBAC, Change-control registry, approval policy, persistence, and
audit middleware remain authoritative. The desktop must not write directly to
Postgres, construct a client-authored audit event, call the operator CLI, or
edit or apply desired-state content.

## Threats and required controls

| Threat | Required desktop control | Authoritative evidence |
| --- | --- | --- |
| A stale selection or confused-deputy action targets a different Change request. | Every mutation carries one exact Change request ID and a case-sensitive typed confirmation. The backend reloads that request immediately before submission, compares the confirmation, and rejects a server response for a different request or Fleet. | Refreshed Change detail plus the server response and subsequent Activity refresh. |
| Double-click, render replay, or concurrent calls duplicate a mutation. | The backend admits one active submission per Change request and action. The interface visibly disables the pending action. Mutations have no automatic retry; retry is explicit after the prior call resolves. | Request-count tests at the mutual-TLS Admin API seam. |
| The desktop bypasses multi-Operator or risk approval policy. | `authorize` submits exactly one approval with the Operator's justification and bounded rollout specification. It never synthesizes another Operator, predicts authorization, or locally changes approval state. Pending approval and forbidden responses remain server results. | Server-returned authorization/Change detail and Activity only. |
| An unbounded rollout amplifies fleet impact. | Attempt limit and maximum concurrency must be positive. Maximum concurrency must not exceed the refreshed frozen-target count or the desktop hard cap of 100. Validity must end after it starts and may span at most 30 days. Execution-window weekdays, start minute, and duration are validated before a request is sent. | The server still performs its own rollout validation and lease enforcement. |
| Lifecycle controls are mistaken for completion or convergence. | Pause, resume, and revoke use exact-ID confirmation, show the server-returned authorization state, refresh Change detail and Activity, and never claim Endpoint convergence. | Change detail and later Sync/outcome evidence. |
| Baseline promotion selects a resource outside the frozen request or hides outcome exceptions. | The backend requires an exact resource address present in the refreshed request with `baseline_eligible=true`, requires case-sensitive resource-address confirmation, displays desired hash/provider/risk, and requires explicit exception acknowledgement whenever any frozen target is failed, blocked, or not seen. It sends no wildcard or locally inferred hash. | Server baseline authorization and server audit evidence. |
| Baseline adoption is redirected to another Fleet or changed after review. | The Go backend reads a native-selected JSON plan once with a 1 MiB limit, parses and validates its exact Fleet/resources/targets, and retains an opaque digest-bound pending plan rather than trusting plan bytes returned from the webview. Submission requires the exact Fleet confirmation and consumes the pending plan once. No repository or server desired-state file is edited. | Native plan preview, exact server response, and Activity refresh. |
| A malformed or oversized plan exhausts memory or smuggles unrelated input. | The native reader rejects empty, oversized, trailing, duplicate/invalid, or Fleet-mismatched plan input before any API mutation. Only typed plan fields enter the backend; no file content is rendered as markup or executed. | Bounded parser tests and a bounded fuzz property for plan input. |
| Polling synchronizes clients, runs while hidden, or produces nondeterministic tests. | Watch uses an injected scheduler and injected phase-jitter source with one in-flight read, a positive bounded interval and timeout, cancellation on selection/profile change, no mutation retry, and no polling while hidden. Tests advance a fake clock and fixed random source and contain no wall-clock sleeps. | Deterministic rendered-workspace tests for jittered cadence, refresh, stale retention, visibility, and timeout. |
| A failed mutation is recorded as successful or a client event is fabricated. | Server audit annotation is attached only after the registry mutation succeeds. The desktop refreshes Activity after success and presents failures without adding local audit rows. | Admin API regression tests and server-returned Activity. |
| Sensitive credentials or baseline content escape through diagnostics. | The workflow uses the existing selected credential in the native HTTP client. Errors and view models contain identifiers, hashes, rollout controls, and outcomes only; no certificate key, token, raw request header, or unrestricted file bytes are logged or persisted. | Secret-canary/error tests and view-model inventory. |

## Abuse and recovery cases

- Invalid, missing, out-of-bounds, or mismatched confirmation input sends no
  mutation request and returns field-specific guidance.
- HTTP 401/403, conflict, persistence failure, cancellation, and transport
  failure leave the last server snapshot visible and do not imply success.
- A second approval by the same Operator, a pending multi-Operator approval,
  and a pre-existing authorization remain server-defined results; the desktop
  does not attempt to repair or bypass them.
- Baseline exception acknowledgement is scoped to the selected request and
  resource. Changing either selection clears it and all typed confirmations.
- Profile switching cancels watch work and clears every pending adoption plan
  and confirmation.

## Verification selected before implementation

- Focused Go mutual-TLS integration tests for every mutation, exact request
  bodies, response-identity checks, one-in-flight behavior, malformed input,
  unauthenticated/forbidden results, audit truth, and native plan bounds.
- A bounded fuzz property for baseline adoption plan parsing.
- Rendered Change-control tests driven by a fake scheduler for watch cadence,
  hidden-window behavior, stale evidence, pending controls, confirmations,
  approvals, exception acknowledgement, and server Activity refresh.
- The desktop Go suite, frontend suite/build, repository `make test`, strict
  OpenSpec validation, and parity-inventory verification before check-off.

No authenticated Fleet load-harness scenario is selected for this slice: the
watch is an interactive Operator read of one exact Change request, not an
Endpoint Sync or fleet fan-out path. It is capped at 60 seconds and one request
in flight, and its injected 10% cadence jitter prevents a same-phase desktop
start from becoming a synchronized fixed-interval stream. The change's later
authenticated load gate remains responsible for fleet-request amplification.

## Residual risk and disposition

The desktop cannot make a distributed approval or rollout safe by itself; it
can only preserve the server contract and fail closed around its inputs. The
existing server lifecycle handler currently annotates pause/resume/revoke audit
context before checking the registry error. That ordering must be corrected
and regression-tested in this item so failed mutations cannot acquire a
success-shaped audit annotation. With that correction and the controls above,
implementation may proceed.
