# 12.5 application-package parity — red evidence

- Mapped workflows: `remotr app package validate`, `remotr app publish`, `remotr app list`, `remotr app show`, `remotr app delete`, `remotr package create`, and `remotr package build`.
- Verification IDs: OS-DOA-019, OS-DFA-001 through OS-DFA-004, OS-DFA-026 through OS-DFA-028.
- Public seam: typed native file/directory selection and shared `internal/apppackages` creation, build, validation, authenticated catalog, upload, detail, and exact deletion operations.
- Selected layers: local filesystem integration, authenticated mTLS Admin API integration, unsafe path/symlink negatives, exact publish/delete confirmation, archive revalidation, Git-index preservation, protected-byte and credential canaries, bounded fuzz validation, and a semantic package workflow.
- Authority boundary: the desktop never shells out to `remotr`, never stages or commits package content, and never exposes archive or credential bytes to ordinary frontend state.

## Intended backend red

Commands:

`cd desktop && go test ./... -run '^(TestApplicationPackageNativeWorkflowBuildsAndValidatesWithoutGitOrServerMutation|TestApplicationPackageCatalogParityUsesAuthenticatedBytesAndExactDeletionScope)$'`

The tests failed to compile because the typed application-package service, native dialog contract, App injection option, local create/build/select methods, and authenticated list/show/publish/delete methods did not exist. This was the intended failure at the public native-filesystem and authenticated Admin API seams.

## Intended frontend red

Command:

`cd desktop/frontend && pnpm exec vitest run src/actions/ApplicationPackageFlow.test.tsx`

Vitest failed to resolve the application-package workflow component. This was the intended failure proving the validate, publish, inspect, exact-delete, scaffold, and build surface was absent.
