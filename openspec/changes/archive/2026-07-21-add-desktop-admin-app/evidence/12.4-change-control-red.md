# 12.4 Change-control parity red evidence

## Audit truth slice

- Public seam: authenticated Admin API lifecycle request and durable audit log.
- Verification IDs: OS-DFA-004, OS-DFA-026, OS-DFA-027.
- Command: `go test ./internal/server -run '^TestFailedChangeLifecycleDoesNotAcquireSuccessAuditAnnotation$' -count=1`
- Intended red: a failed pause of a missing Change request was recorded as
  `admin.change.pause` for resource `missing`, rather than a generic failed API
  request. This proved the success annotation preceded registry success.
- Follow-up command: `go test ./internal/server -run '^TestPendingChangeApprovalAuditRetainsExactRequestIdentity$' -count=1`
- Follow-up red: the first valid approval of a two-Operator request recorded
  `admin.change.authorize` with an empty resource ID because the compatibility
  response has no rollout authorization until the approval threshold is met.

## Native Change-control slice

- Public seam: purpose-specific App methods over a selected mutual-TLS Admin
  API session and the native baseline-adoption file chooser.
- Verification IDs: OS-DOA-016, OS-DOA-017, OS-DOA-019, OS-DFA-001 through
  OS-DFA-004, and OS-DFA-026 through OS-DFA-028.
- Command: `cd desktop && go test ./... -run '^TestChangeControlParityPreservesApprovalAndExactMutationScope$' -count=1`
- Intended red: the test did not compile because `ChangeAuthorizationRequest`,
  `ChangeExecutionWindowInput`, the Change-control App methods, and the native
  adoption-plan binding did not exist. This establishes that no desktop
  mutation seam was already present.

## Rendered deterministic-watch slice

- Public seam: Change request detail workspace with an injected refresh clock
  and visibility boundary.
- Verification IDs: OS-DFV-022, OS-DFV-023, OS-DFV-027 through OS-DFV-029,
  and OS-DFA-001 through OS-DFA-004, OS-DFA-026, and OS-DFA-027.
- Command: `cd desktop/frontend && pnpm exec vitest run src/changes/ChangeControlFlow.test.tsx`
- Intended red: the current surface still rendered `Read-only evidence` and
  provided no Change-control action region, proving that watch, approval,
  lifecycle, promotion, adoption, and Activity-refresh controls were absent.
- Timeout regression red: a fake-clock advance to the 60-second deadline left
  watch active when its prior read was still in flight. The deadline check was
  moved ahead of the one-in-flight guard so timeout deterministically cancels
  observation without starting or waiting for another read.
- Cadence regression red: an injected maximum random sample still scheduled
  the fixed 2,000 ms interval instead of the expected bounded 2,200 ms phase
  jitter. Watch now injects both scheduler and random source, while a separate
  deadline callback preserves an exact deterministic 60-second stop.
- Accepted-result red: a single-Operator authorization rendered the generic
  `Rollout authorized` acknowledgement but no `Accepted rollout authorization`
  region, so the server's exact validity, attempt/concurrency bounds, recurring
  window, actor, time, and authorization ID were not inspectable. The result
  view now preserves and renders those server-returned fields.
